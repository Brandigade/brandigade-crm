The data moved into tables. `workspace_state` is now a read-only backup, and writing to it would lose edits.

Brandigade CRM: Brandigade's own shared CRM (one company, roles owner/admin/editor/viewer; editors change only their own records, see ARCHITECTURE §3). Read `docs/ARCHITECTURE.md` before changing anything; it is the source of truth for structure, schema, hooks and security rules.

## Stack
- Front end: `index.html` + `css/*.css` + `js/*.js`, vanilla JS, classic scripts sharing one global scope (order in `index.html`: data.js, demo.js, app.js, timeline.js, email.js, notifications.js, dialer.js). No bundler. `config.js` (Supabase URL + anon key) is generated by `npm run build` / served by `npm run dev`.
- Server: one Supabase Edge Function `api` (`supabase/functions/api`, built from `lib/server` by `npm run build:edge`) → `lib/server/routes.ts` (Web Request/Response). Feature code in `lib/server/email`, `notifications`, `voice`. Locally `npm run dev` serves the same code on `/api`.
- Supabase: Postgres + RLS, Auth, Realtime, Storage, pg_cron (calls `/api/cron/tick` every minute). Schema only in `supabase/migrations/`.
- The site is on GitHub Pages. `.github/workflows/deploy.yml` runs the tests, and on `main` deploys the database, the Edge Function and the site; settings are GitHub secrets (SETUP.md).

## Data
- CRM records live in tables: companies, contacts (leads), deals, tasks, activities (the unified timeline). `workspace_state` is the old JSON document, frozen read-only as a backup.
- In the browser, `state` keeps camelCase records; `js/data.js` maps them to tables, saves only changed rows (`saveState()`), and applies realtime changes.
- Emails, calls and task changes reach the timeline through database triggers. Never insert those activities yourself.

## Rules to keep
1. Edit `state`, call `saveState()`, re-render. Owner settings: `saveSettings()`.
2. Wrap data-changing handlers in `guardEdit()` / `guardOwnerOnly()`. RLS and the server are the real protection: every new table needs policies, explicit grants and a test in `tests/sql/`.
3. Never put a secret in the front end; server secrets only through `lib/server/env.ts`.
4. Escape user and provider text with `escapeHtml()` before `innerHTML`; untrusted HTML only in a sandboxed iframe.
5. Controls viewers keep need `data-always-enabled="true"`; call `applyRolePermissions()` after rendering controls.
6. No `alert()`/`confirm()`: use `notify()` and `await confirmDialog()`.
7. Colours come from the CSS tokens in `css/app.css`.
8. Never edit an applied migration. Add a new timestamped file.
9. Feature modules plug into screens through `CRMHooks` (see ARCHITECTURE §6) rather than editing `js/app.js`.

## Demo mode and tests
`createDemoClient()` (`js/demo.js`) is an in-browser stand-in for the Supabase client. Demo mode and `tests/app/test_crm.cjs` run on it; keep it in sync with new table calls and RPCs.
Run `npm run typecheck && npm run lint && npm test && npm run test:db` after changes, and `npm run test:e2e` for UI flows (local Supabase). Take a Playwright screenshot for layout work.
